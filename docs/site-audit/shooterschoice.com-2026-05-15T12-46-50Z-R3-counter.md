- **Caller line 732:** `const remaining = products.filter(p => !handledIds.has(p.id));`  — empty set when all chunks "handled" OOS.

**RULING:** Both sides are partially correct, but R2 (this batch) is operationally right. The 537–546 guard correctly prevents DEACTIVATION (prior R3 was correct on that narrow point). But because line 549 unconditionally pushes to `handledProductIds`, the caller at line 711 returns early WITHOUT calling Playwright. Result: OOS products' `lastSeenAt`, `staleSince`, `staleVerifiedAt`, `verifyErrors`, `stockStatus`, `price` are NEVER updated for the entire 6,877-product OOS subset on this site.

This is exactly the project pitfall stated in CLAUDE.md: "WooCommerce Store API only returns in-stock items — 'not in Store API' = out of stock". It is a SILENT LOSS-OF-SIGNAL bug, not a deactivation bug. Restock detection (OOS→instock transition) cannot fire because `stockStatus` never refreshes. The prior R3 missed this because it only looked at lines 537–546 in isolation; it did not trace the unconditional `handledProductIds.push` on line 549 nor the caller's early-return on line 711.

**Verdict on cross-batch contradiction:** R2 (this batch) wins. `verifyMethod: json-ld` (DB value) is correct for sites with significant OOS population. The prior R3's "store-api is safe" verdict is BROKEN — it stops at the guard without tracing the early-return.
