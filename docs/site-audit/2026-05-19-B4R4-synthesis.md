## B. Cross-cutting lessons learned by artifact

### B1. SKILL.md gaps (12 items, biggest first)

1. **Skill must verify every emitted `catalogUrl` returns 200 AND product content (NOT a WP/404 template) right before promoting.** 3 sites (gotenda, hical, greatnorth) had DB slugs that are 404 today. Hical's `/firearms/` is iPhone-UA soft-200 with "Page not found" title — Skill needs a content check, not just status.

2. **Per-category pagination check requires walking TO page 2.** R2 hit "lastPage=1, curated landing" trap on gotenda's renamed slugs by reading only the page-1 hero block. Many WC themes render hero treatment on page 1; full pagination from `/page/2/` onward. Skill must force `/page/2/` (or `?paged=2`) probe before concluding "lastPage=1".

3. **Skill must paginate Store API/WP REST taxonomy lists to `x-wp-totalpages`.** Gotenda R2 read only page 1 of `/wp-json/wc/store/v1/products/categories` (172 entries across 2 pages) — concluded "1 top-level category" → recommended single `/shop/`. R3 walked page 2 → 8 real top-level cats summing to 15,913.

4. **Skill must probe `searchUrl` deterministically.** 5/10 batch-4 sites had DB searchUrl that R1 missed (canadasgunstore, doctordeals, nordic, greatnorth, cfa) — and canadasgunstore's DB value was itself 404. Stage 3 should always check the homepage `<form>` action + WP/WC defaults (`/?s=&post_type=product`, `/search.php?search_query=`, platform-native search).

5. **Klevu canonical paths require live SSR'd `klevu_pageCategory` scrape per category.** Nav-derived shallow paths lose firearm-relevance granularity (alflahertys: 8 deep DB paths match SSR'd JS var verbatim). Skill must fetch each category page and extract `klevu_pageCategory` JS var (despite the field being runtime-inert today — see B2 #3).

6. **`productCountMethod` shape MUST match the runtime switch enumeration verbatim.** `sitemap` reads scalar `m.url`; `sitemap-index` iterates `m.urls`. Mixing them silently breaks (nordic, wolverine, hical). Skill needs a stage 8 validator that emits ONLY the 11 canonical method names + their required fields, and rejects any other shape.

7. **WP REST and Store API have DIFFERENT date-filter parameter names.** WP REST `/wp/v2/product` uses `?modified_after=`; Store API `/wc/store/v1/products` requires `?after=` and silently ignores `?modified_after=` (returns full result set — hical R3). Skill must record `dateFilterField` PAIRED with `dateFilterApi` and document both surface conventions.

8. **WC count: WP REST `x-wp-total` and Store API `x-wp-total` answer different questions.** WP REST counts ALL `status=publish` products (incl. catalog-hidden + drafts); Store API counts customer-facing in-stock only. Both can be "correct" yet differ wildly (canadafirstammo: 962 vs 132 = 7×; greatnorth: 4306 vs 528 = 8×). Skill must specify WHICH surface the `expectedProductCount` comes from, AND the choice must match `verifyMethod` (Store-API count ↔ `store-api` verify; WP-REST count ↔ `detail-page` verify with hidden-archive tolerance).

9. **WAF severity is BOTH IP-dependent AND UA-dependent.** Same site returns 200 with Safari/Firefox UAs and 403 with Chrome/Edge UAs in the same window (g4c). Heavy probe must use the production UA rotation pool (`http-client.ts:9-14`), not just `curl/default` or a single test UA. If specific UAs in the pool trigger CF after a sustained pattern, `userAgentOverride` must be set to one that doesn't. R2's `wafProbeEvidence.rapidBurstTested:false` was the load-bearing gap on g4c.

10. **`hasWaf:true` defensive flag with `wafType:cloudflare-passive` hit 4-5/10 sites.** DB column and `wafType` can disagree silently — operator flipped wafType from Sucuri to cloudflare-passive without flipping the column (alflahertys still has stale `wafWorkaround:sucuri-cookie-cache`). Skill must emit BOTH fields together AND SKILL.md must call out that the column flip is required when changing wafType. Runtime cost of false `true`: perPage 50→20 throttle (when `profile.perPage` is null), Playwright fallback always engaged, WAF cookie cache used.

11. **`topLevelCategories.allOption` numbers must come from the SAME surface as `expectedProductCount`.** Canadafirstammo had WP-REST-derived allOption (firearms 203) that was 3-13× customer-visible counts (live 16). Skill must derive both from the same API per-category and document the source.

12. **Skill should distinguish "operator override" siteProfile shapes from "default mapping" shapes.** g4cgunstore's `adapterType=generic-retail` on a WC site is intentional (operator-routed for extraction-pipeline reasons; both adapters consume `catalogUrls`). Skill's table mapping platform → adapterType is correct as default but must record that the OPERATOR can override and the OVERRIDE doesn't trigger any runtime mismatch warning (B2 #2). Mark the choice as `adapterTypeOverride: true` in `auditNotes`.

### B2. Runtime code bugs (file separately — not pre-bootstrap concern)

1. **`product-count-probe.ts:239` `parseInt` truncates comma-bearing numbers.** `parseInt("2,384", 10) === 2`. Fix: `parseInt(matched[1].replace(/,/g, ''), 10)`. Surgical one-line fix, generic, no regressions on no-comma totals. Affects canadasgunstore today; would affect any site emitting `"N,NNN found"` strings.

2. **`adapter-registry-mismatch.ts:19-30` warns only on `crawlers.catalog.method != adapterType`.** Does NOT warn on `platform != adapterType` mismatch. WC-platform + `adapterType=generic-retail` is silently accepted (g4cgunstore). Add a `platform != adapterType` branch (or document that this combination is intentional and operator-controlled).

3. **`_resolveKlevuCategoryPath` at `generic-retail.ts:288` is DEAD CODE.** Declared but never invoked. Live Klevu fetch at L387 uses global wildcard SEARCH (`query:{term:'*'}`) — never filters by category. `klevuCategoryPaths` profile field is documentation-only. **Action**: either wire it into the live fetch path OR delete it + the supporting profile field. Currently confusing for both auditors and future maintainers.

4. **`generic-retail.ts:300` HTML-entity decode only handles `&amp;` → `&`.** Doesn't decode `&#x27;` (apostrophe), `&quot;`, `&lt;`, `&gt;`, or numeric entities. Theoretical today because the containing method is dead code (B2 #3). Load-bearing footgun if it's ever wired in — alflahertys has a real category `"Al's Bargains"` rendering as `"Al&#x27;s Bargains"`. Use `he.decode()` or `decode-html-entities` package.

5. **`product-count-probe.ts:132 validateMethod` throws on unknown method names; caught at TWO catch sites.** `crawl-scheduler.ts:253-265` (logs `[Scheduler] <domain>: product count probe failed: ...`; returns null) AND `product-count-probe.ts:493-497` (returns null in worker context). When the catch returns null and DB `siteProfile.expectedProductCount` is also null, `verifyBootstrapCoverage` computes `ratio=null → isAcceptable=true` at L525 — silent disablement of the coverage gate. Dormant when DB count is populated; activates the moment it's null. **Action**: backfill DB siteProfile to use canonical method names. Batch-3 corrections already moved 5 sites in this direction; batch-4 R4 above adds 3 more (hical, wolverine, nordic).

6. **`worker.ts:769-772` early-returns when `crawlers.maintain.verifyMethod` is missing.** Logs `[VerifyWorker] <domain>: MISSING verifyMethod...; return`. Verify worker is a no-op for any site without this field — wolverine verified live, restock detection broken. **Action**: `profile-validator.ts` must require `crawlers.maintain.verifyMethod` non-empty when promoting to DB.

7. **`worker.ts:544` push inside `if (apiProduct)` branch — post-batch-3 fix verified working.** `else` at L545-555 has NO push; handled-count early-return at L717 can no longer mask missed products. Greatnorth R3 explicitly traced this end-to-end on the now-merged `fix/batch-3-runtime-bugs-2026-05-19` branch. Fix is real and effective.

### B3. Harness/methodology gaps (R1→R2→R3 process)

1. **R3 adversarial round delivers value when R2 reasoned from a sample.** 7/7 successful counters this batch came from R3 broadening the sample: gotenda's "page 2 looks different from page 1" (R2 sampled only page 1), gotenda's "Store API has 172 entries across 2 pages" (R2 read only page 1), canadafirstammo's "WP REST counts hidden+drafts" (R2 used wrong surface), g4c's "Chrome UA escalates after sustained pattern" (R2 single-moment matrix). Pattern: **R2 sampling is the highest-value target for R3 to attack.**

2. **Heavy WAF probe needs a sustained-pattern test, not just a multi-UA matrix snapshot.** g4c proved CF escalation kicks in after ~60s of crawl-like requests with the deterministic-bad-UA (Chrome 120 for that site). Heavy probe must walk `/shop/page/N/` for 50+ pages with the actual production UA, not just hit `/` once.

3. **Always check `x-wp-totalpages` and walk all pages of any taxonomy/category index.** Gotenda demonstrated single-page-read of `/wp-json/wc/store/v1/products/categories` → 1 top-level cat → wrong recommendation. WP REST and WC Store API both default to per_page=10 — easy to miss.

4. **R3 caught two "R2 number right but explanation wrong" cases.** (a) Hical's "Store API ignores modified_after — needs `after`" (runtime already does correct thing — narrative bug, not a code bug). (b) Canadafirstammo's "perPage 20-vs-50 throttle doesn't fire because profile.perPage=12 short-circuits the `||`". Synthesis must distinguish **number wrong** (changes DB) from **narrative wrong** (changes documentation only). Both worth recording but only the number is load-bearing.

5. **Subagent harness blocks R3 from running auth-attempt / path-traversal / large-body POSTs / shellshock probes** as unauthorized scouting. Wolverine R3 substituted passive `__cf_bm` + `cf-cache-status:DYNAMIC` fingerprint evidence; classifies as "couldn't disprove with available tools" not "couldn't disprove fundamentally." Synthesis must mark these untested attack surfaces explicitly so R4 doesn't claim "WAF behavior fully verified."

6. **Persona-injected agents found bugs the same-persona implementer missed.** R2 (testing-api-tester) and R3 (engineering-code-reviewer) work on overlapping evidence with different mindsets. R3's "trace the cited code line in full context, not just the cited line" caught 4 of canadafirstammo's R2 corrections needing revision. The role-switch IS the value, not just the rerun.

7. **Cross-batch R3 verification continues to pay.** Batch-3 R4 lesson "always trace BOTH branches of conditional gates" (worker.ts:381-400, L549, L711, L759-769) was re-applied this batch and confirmed the worker.ts:544 fix is real and effective (greatnorth). Without the meta-pass, the fix's actual effectiveness on production data would be assumed, not verified.

8. **WC `?modified_after=` (WP REST) vs `?after=` (Store API) divergence is a load-bearing platform footgun** (hical). SKILL.md table mapping per-platform date-filter param exists for some surfaces but is incomplete. **Action**: skill table must specify dateFilter param per API surface, not per platform alone.

**Bottom line:** 7 R3 counters this batch (gotenda × 1, canadafirstammo × 4, g4cgunstore × 1, canadasgunstore × 1 minor) on top of 43 R1-wins / 28 DB-wins / 9 other from R2 — confirms the 4-round design surfaces bugs even after the implementer + reviewer roles agreed. Highest-impact corrections to load-bear: **canadafirstammo expectedProductCount 962 → 132** (would prevent bootstrap-stuck-forever), **gotenda catalogUrls collapse → 8 per-category** (would prevent silent 99.7% coverage collapse), **g4cgunstore userAgentOverride** (would prevent steady-state 403 wall), **wolverine + nordic + hical productCountMethod shape** (would prevent silent coverage gate disablement). Operator decisions needed: (a) verifyMethod policy per site (store-api fast + silent loss-of-signal vs detail-page slow + complete coverage); (b) catalogUrls strategy (umbrella vs per-category) per site for token-allocation tradeoffs; (c) klevuCategoryPaths — wire `_resolveKlevuCategoryPath` live or delete the field documentation.
