## Critical Lessons (from real incidents)

- **Ecwid-on-WordPress (Mistake 31) — drive the live UI to capture real API field names; prior guess-based audit was wrong.** Detection: `<script src="https://app.ecwid.com/script.js?<storeId>">` + `ec-store` classes + `wp-content/plugins/ecwid-shopping-cart/` assets. Store ID is the 7-8 digit integer from the script URL. **Real storefront API (undocumented, no auth)**: `POST https://us-vir2-storefront-api.ecwid.com/storefront/api/v1/<storeId>/catalog/search` (global) or `/catalog` (per-category) with body `{lang:'en', pagination:{offset,limit}, sortBy:'<value>', parentCategoryId?:<id>, urlParams:{baseUrl:'/store/', canonicalBaseUrl, isCleanUrls:true, isCanonicalUrlsEnabled:true, isSlugsWithoutIds:false}}` + headers `Origin`/`Referer` pointing at merchant WP site. Returns `{products:[], totalProductsCount}`; product URL is in `product.seo.canonicalUrl`; NO date fields on products. **Sort field is `sortBy`** (NOT `sortOrder`), **values are camelCase** (`addedTimeDesc`, `priceAsc`, `priceDesc`, `nameAsc`, `nameDesc`, empty string = merchant-default "We recommend"). **Pagination**: `pagination.offset` + `pagination.limit` body fields, max 200 per request. **Category filter**: top-level `parentCategoryId` body field (NOT nested `filtering.categoriesFilter`). Verified 2026-04-09 on triggersandbows.com via Playwright XHR intercept of the live sort dropdown (`<select id="ec-products-sort">`) + pagination click (`.pager__button--next`) — see `backend/scripts/tb-real-ui4.ts`. Global walk via `/catalog/search` with offset=0..4800 limit=200 returned 4,914 unique products matching `totalProductsCount`. Sort monotonicity proven: `addedTimeDesc` → `CG-0239, CG-0238, CG-0237` (descending consignment IDs). **Critical lesson from this audit**: the PRIOR (wrong) audit guessed field names from Ecwid's v3 REST docs (`sortOrder: ADDED_TIME_DESC` uppercase) and falsely concluded sort/filter were impossible. **NEVER guess API field names for an SPA's internal API — drive the live UI (click sort dropdown, click pagination, scroll) with `page.on('request', ...)` intercept, and capture the real POST body byte-for-byte.** Mistake 2 (read the HTML) extends to SPAs as "capture the XHR". Reference: playbook Mistake 31, `backend/scripts/tb-real-ui4.ts` (canonical Ecwid UI-drive discovery harness).

- **Cross-reference DOM ordering against known signals before declaring "no sort possible."** On 2026-04-07 an earlier audit pass declared irunguns.ca needed `full-catalog-sweep` because no sort `<select>` exists on category pages. The user pushed back. A one-GET cross-reference proved the DOM first product slug on Rifles (`glenfield-model-a-moss-green-308-win-20-barrel-4-rounds`) matched a previously-captured POST endpoint baseline first slug — proving natural DOM order is `p.id DESC` (newest-first). This unlocked `navigate-from-watermark` with zero new infrastructure. Lesson: when no sort UI exists on a custom-PHP/legacy site, run ONE cross-reference test (DOM first slug vs. any independent newest-first signal — POST endpoint baseline, sitemap lastmod, RSS, known-recent product) before concluding `navigate-from-watermark` is impossible. "No sort UI" ≠ "no sort possible". Ref: `.claude/catalog-url-discovery-playbook.md` Mistake 15 sub-lesson + Mistake 18, irunguns.ca profile notes.

- **Test the production Playwright fallback BEFORE declaring a SPA site "blocked".** On 2026-04-07, two consecutive audits on liangjian.ca (GoDaddy OLS) saw `extractCatalogProducts` return 0 from plain axios HTML and immediately wrote `siteProfile.crawlers.watermark.blockedReason: 'godaddy-ols-spa-api-on-foreign-origin'` into the profile + recommended a new GoDaddyOlsAdapter. Both audits even ran Playwright manually, saw 15 products render, AND STILL declared the site blocked. Truth: the GoDaddy OLS selector `[data-aid="PRODUCT_LIST_RENDERED"] [data-ux="GridCell"]` was already in `generic-retail.ts:431`. The production `fetchWithPlaywright()` fallback at `catalog-crawler.ts:403-413` and `watermark-crawler.ts:143-159` auto-fires when static HTML > 5KB returns 0 products. The site needed `needsPlaywright: true` in the profile and zero new code. The earlier audit's own profile note `lastWatermarkUrl: ".../glock-2141-...?orderby=date"` was proof a prior crawl had succeeded — missed by both auditors. Lesson: when static HTML returns 0 products from a site a human can browse, you MUST (1) run `fetchWithPlaywright()` against the same URL, (2) run `extractCatalogProducts` on the rendered HTML, (3) check `generic-retail.ts` for an existing platform selector (Klevu, GoDaddy OLS, BigCommerce Stencil, Shoplightspeed, etc.), (4) check the existing `lastWatermarkUrl` for evidence of a prior successful crawl. Only AFTER all four fail can you propose a new adapter. The cost of one Playwright probe is ~7s; the cost of declaring a site blocked when it isn't is weeks of silent under-coverage. Always pay the 7 seconds. Ref: liangjian.ca profile, `generic-retail.ts:431`, `catalog-crawler.ts:403-413`, `watermark-crawler.ts:143-159`, playbook Mistake 19.

- **When investigating a SPA, drive Playwright as a real user — don't just static-fetch.** On 2026-04-07 three consecutive audits of liangjian.ca (GoDaddy OLS) declared "no sort exists" because they only did `page.goto()` + `waitForSelector` and scanned the static HTML for `<select>` elements. The sort dropdown was visible the entire time as `[data-aid="PRODUCT_SORT_DROPDOWN"]` but its handler lives in JS, not markup — static scans see nothing. A live Playwright session that actually `page.click()`-ed the dropdown immediately revealed: (a) URL updated to `?sortOption=descend_by_created_at`, (b) an XHR fired to `mysimplestore.com/api/v2/products?...q[descend_by_created_at]=true` — two wins in one click. Lesson: when a site is a SPA, clicking UI controls in a live Playwright session (with `page.on('request', ...)` logging) is a mandatory step before concluding "no sort/filter/paginate param exists." Static HTML scans are the right first step for server-rendered sites; they are the wrong first step for SPAs. Ref: liangjian.ca profile, playbook Mistake 19 sub-lesson.

- **Pre-bootstrap probe must report `testUrlWasFacetFiltered` + derive `expectedProductCount` so the skill can detect facet-subset counts on Drupal classifieds (Mistake 37, 2026-04-15).** On 2026-04-15 a dry-run of `/pre-bootstrap` against gunpost.ca (Drupal 10 classifieds, 30K+ listings, Cloudflare rule-selective active) against ground-truth manual audit exposed THREE judgment-layer gaps that the probe's existing mechanical output alone could not close: (1) **Test URL biased to a facet**: `robots.txt` Disallows `/ads` AND Cloudflare serves an interactive challenge on the bare `/ads` URL, while any facet-filtered variant (`/ads?f[0]=c:1` = Firearms facet) passes through. The probe's Phase 3 extraction test correctly switched to the facet URL (10 products extracted successfully), but this biased Phase 5 sort discovery AND Phase 6 pagination `totalPagesObserved: 702` (Firearms facet only, not the global 1692-page catalog). The skill had no mechanical signal that this happened — it had to be inferred by scanning the testUrl string for `f[0]=` or `category=` patterns. (2) **Sort form names differ between bare and facet URLs**: Drupal Views exposes `?sort_by=<col>&sort_order=DESC` on the bare `/ads` (the "exposed form") AND `?sort=<col>&order=desc` on facet-filtered `/ads?f[0]=c:N` (anchor-pair form). The probe correctly detected `sort=created&order=desc` from the facet URL — but the manual audit's canonical `sortParam` is `?sort_by=date_pub&sort_order=DESC` (from bare). Both are valid Drupal Views sort forms of the same column. The skill needed explicit guidance to re-read the bare URL's `<select>` when the facet URL was used, and to prefer the exposed-form param names for the global catalogUrl. (3) **Sitemap count lags live listing by ~25%**: gunpost sitemap classification returned 22,739 products. Live `/ads?sort_by=date_pub&sort_order=DESC` walk shows 1691 pages × 18 + 3 last-page items = 30,423 — a 25% undercount. Root cause: classifieds keep sold/expired listings visible on the live index for a grace window (with `sold` CSS class), but sitemap regeneration drops them immediately. **Fixes applied 2026-04-15**: probe `AssemblyPhase` now emits `expectedProductCount` + `expectedProductCountSource` (`'api' | 'pagination-walk' | 'sitemap' | null`) + `testUrlWasFacetFiltered`, with priority api > pagination-walk (only when not facet-filtered) > sitemap. Reference: `backend/scripts/pre-bootstrap-probe.ts` (assembly improvements 2026-04-15), `.claude/skills/pre-bootstrap/SKILL.md` new "Drupal classifieds" section, gunpost.ca profile.

- **Pre-bootstrap probe script must use native-fetch fallback for HPE errors; the heavy-WAF probe output parser must scan only actual header lines (Mistake 36, 2026-04-15).** On 2026-04-15 a dry-run of `/pre-bootstrap` against bullseyenorth.com (Celerant ColdFusion) exposed TWO critical probe defects: (1) **HPE cascade**: raw `axios.get()` in `backend/scripts/pre-bootstrap-probe.ts` failed with `Parse Error: Invalid header token` on every fetch because Celerant sends trailing-space headers like `X-Frame-Options : SAMEORIGIN` that break Node's llhttp parser. This cascaded across all phases. The production `http-client.ts:344-347` already has a native-fetch fallback for this; the probe did not. Fix: added `nativeFetchText()` + HPE-detection branch to `safeFetch()`/`safeFetchJson()` matching the production pattern. (2) **WAF parser false positive**: naive `/x-sucuri/i.test(probeOutput)` on the ENTIRE `heavy-waf-probe.sh` output matched the INTERPRETATION GUIDE trailer text — producing a FALSE `hasWaf: true, wafType: 'sucuri'` on a site with no WAF. Fix: rewrote `probeAccess()` to extract the BATCH 1 header block only (via `=== BATCH 1: ... ===(.*?)(?=\n=== BATCH)` regex), filter to lines starting with `<header-name>:`, then match actual header lines with anchored regexes (`^cf-ray:`, `^x-sucuri-(id|cache|block):`, `^server:\s*cloudflare`, cookie markers `^set-cookie:\s*(visid_incap|incap_ses|...)`). Additional probe fixes (sort-path scheme, newest-candidate disambiguation, testUrl sort bias, sitemap product-count filter) all in same file. Reference: `backend/scripts/pre-bootstrap-probe.ts` full rewrite 2026-04-15; bullseyenorth.com ground-truth harness; `.claude/skills/pre-bootstrap/SKILL.md` new "Celerant / ColdFusion storefronts" section.

## Rules
- NEVER guess API field names for an SPA's internal API — drive the live UI with `page.on('request', ...)` intercept and capture the real POST body byte-for-byte.
- For server-rendered sites, static HTML scan is the right first step. For SPAs, `page.click()` controls is mandatory before concluding "no sort/filter exists".
- Always cross-reference DOM ordering against an independent newest-first signal before concluding "no sort possible".
- Test the production Playwright fallback BEFORE declaring a SPA site "blocked" — `fetchWithPlaywright()` auto-fires when static HTML > 5KB returns 0 products.
- Probe code must use native-fetch fallback for HPE errors and must parse WAF headers from BATCH 1 only (not the interpretation guide).
