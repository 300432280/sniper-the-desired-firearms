You are working on the FirearmAlert project — a Canadian firearms retail monitoring app crawling 60+ sites. This persona covers backend infrastructure, the adapter framework, and platform-specific extraction quirks.

## Your Domain
- **Express API** (`backend/src/routes/`) — auth, searches, admin endpoints
- **Prisma ORM** (`backend/prisma/schema.prisma`) — PostgreSQL via Neon
- **BullMQ workers** (`backend/src/services/worker.ts`) — job queue with Redis/Upstash
- **Crawl scheduler** (`backend/src/services/crawl-scheduler.ts`) — 2-min tick, safety ceilings
- **Token budget** (`backend/src/services/token-budget.ts`) — per-site hourly request budgets
- **Adapter framework** (`backend/src/services/scraper/adapters/`) — platform-specific scrapers
- **Catalog crawler** (`backend/src/services/catalog-crawler.ts`) — tier-based full catalog refresh
- **Watermark crawler** (`backend/src/services/watermark-crawler.ts`) — Tier 1 new item detection
- **Stream detector** (`backend/src/services/stream-detector.ts`) — per-stream tier engine

## Key Patterns
- Stream-based catalog crawling: each category/endpoint is an independent stream with its own tier structure
- API streams partition by date range (T2: 7d, T3: 8-21d, T4: 22+d); HTML streams partition by page range (T2: 30%, T3: 35%, T4: rest)
- `detectTotalPagesFromHtml()` extracts pagination on first page
- Pressure/capacity model drives crawl intervals: `capacity = e^(-3 * pressure)`
- Per-site `crawlTuning` JSON overrides defaults
- Firearms priority plugin: firearms 3x, ammunition 2x weighting
- Token budget: 60 req/hr default, Tier 1 reserves 70%

## Critical Lessons (from real incidents)

### Stream / tier architecture & HTTP client
- **Never apply page range logic to API streams** — API uses date ranges (T2: 7d, T3: 8-21d, T4: 22+d). Page numbers within each date window are independent and start from 1.
- **Sequential T2→T3→T4 execution is load-bearing** — T2 discovers `totalPages` on first page, which sets ranges for T3/T4 before they start. Breaking this order breaks partitioning.
- **`totalPages` must be stored on the stream object** — `updateStreamPageRanges()` stores it so the pre-crawl check can apply ranges without re-crawling.
- **Single-page streams are valid** — if a category has 1 page, all tiers get that page. Don't error or skip.
- **HTTP 599 / malformed headers** — some sites return headers that break `undici`. The HTTP client has a native `fetch()` fallback for `HPE_INVALID_HEADER_TOKEN` errors.
- **`apiCrawlUsed` flag prevents HTML fallback when API returns empty results (Mistake 34).** If `WooCommerceAdapter.fetchCatalogPage()` returns `{ products: [], totalPages: N }` instead of `null`, `apiCrawlUsed` becomes true and the HTML fallback at `catalog-crawler.ts:327` never fires — the site silently crawls 0 products forever. Trace the exact fallback code path; "architecture says fallback exists" is not proof it fires. Ref: `catalog-crawler.ts:266-327`.

### Sort / pagination / extraction (platform-specific)
- **Never guess URL parameter names for sort/filter/pagination — READ the actual `<select>` and `<form>` HTML first.** On 2026-04-06 I claimed "no date sort exists" on durhamoutdoors.ca after testing 6 guessed param names (`?sort=newest`, `?orderby=date`, etc.) — all returned page-1 products. The site DID have a date sort: `?sortby=4` (option value="4" labeled "Newest"). I never guessed `sortby` so I missed it. The parameter name was right there in the page HTML in `<select id="sortby" name="sortby">`. Reference: `backend/src/services/scraper/adapters/generic-retail.ts` and the durhamoutdoors profile. If you need to find a sort/filter/pagination parameter, fetch the category page and grep the HTML for `<select`, `<form method="get"`, `data-sort`, `onchange`, and `<option>` elements. Print every option's value+text. Then test the candidate param against a known-newest product ID. Do NOT use a list of guessed names as your search strategy.

- **Searchspring overlay hijacks URL sort semantics — sort lives in a URL hash fragment, not a query param.** On 2026-04-08 the audit on sail.ca (Magento 2) initially tried native Magento URL sort params (`?product_list_order=created_at&product_list_dir=desc` plus merchant-customized variants seen on site 18 londerosports) — all returned identical "Best Selling" default. Root cause: sail.ca loads a third-party JS overlay `<script src="//cdn.searchspring.net/search/v3/js/searchspring.catalog.js?s8zq1c">` that replaces the native Magento catalog renderer entirely. When the user clicks "Newest" in the dropdown, Searchspring mutates the URL hash to `#/sort:created_at:desc` and re-fetches from its own JSON API at `https://<siteId>.a.searchspring.io/api/search/search.json`. The native Magento controller never sees a sort param. **ID-jump proof**: hash-sorted page 1 = tikka-t1x-...1618256 (2026), page 22 = sako-gamehead-...1356073 (2024). **Fix**: bake hash fragment into each `catalogUrl` (e.g. `/en/hunting/firearms#/sort:created_at:desc`), set `sortParam: ""` empty, use normal query pagination `{type:'query', template:'page'}`. Node's `URL` class preserves hash fragments through `searchParams.set()`, so `buildPaginatedUrl()` at `catalog-crawler.ts:118-166` works unchanged. **Detection**: grep HTML for `cdn.searchspring.net/search/v3/js/searchspring.catalog.js?<siteId>`. If present on ANY platform (Magento/BC Stencil/Shopify), trust NO URL sort params — render via Playwright, click "Newest" programmatically, capture `page.url()` to discover the real fragment scheme. Ref: playbook Mistake 25, sail.ca profile.

- **Volusion sort param is silently ignored unless `searching=Y` is also present in the URL.** On 2026-04-08 the audit on precisionoptics.net (Volusion legacy eCommerce) read `<select id="SortBy">` and found `value="3"` for Newest — but building `?sort=3&show=90&page=N` returned the default Availability ordering, not newest. The Volusion category controller only honors `sort` when `searching=Y` is ALSO in the query string (visible in `/a/j/productlist.js` `Refine()` which always hardcodes `searching=Y&sort=...`). Correct URL format: `{path}?searching=Y&sort={N}&show={N}&page={N}`. Common Volusion sort values (read the `<select>`, don't guess): `1=Price ASC, 2=Price DESC, 3=Newest, 4=Oldest, 5=Most Popular, 7=Title, 9=Manufacturer, 11=Availability (default)`. Volusion platform signature: `x-powered-by: Volusion` header, `/v/vspfiles/` assets, `/category_s/NNN.htm` category URLs, `/ProductDetails.asp?ProductCode=XXX` product URLs. Ref: playbook Mistake 24, precisionoptics.net profile.

- **Odoo eCommerce signature + sort param + stored platform tags need verification.** On 2026-04-08 the audit on outfitters.goldnloan.com found stored `platform: 'lightspeed'` but the notes field said "Odoo, bilingual" — nobody cross-validated. Site is actually Odoo (markers: `<meta name="generator" content="Odoo">`, `oe_website_sale`, `oe_currency_value`, theme classes `tp-product-item`). Odoo sort param uses literal `+` for space: `?order=create_date+desc` (Newest), `website_sequence+asc` (default), `name+asc`, `list_price+asc|desc`. Read the `<a href="?order=...">` sort dropdown before writing. Pagination is `path` type `/page/{N}`. Sitemap over-counts by ~5-10% vs catalog walk due to `hide_out_of_stock=1` storefront filter. Catalog walk is ground truth, not sitemap. **Fleet observation**: 11/21 sites have had wrong WAF flags OR wrong platform tags at onboarding — always grep HTML for `<meta name="generator">` + known platform markers before trusting stored `platform`. Ref: playbook Mistake 22.

- **OpenCart's visible sort dropdown is incomplete — always probe `?sort=p.date_added&order=DESC` directly.** On 2026-04-08 the audit on northprosports.com (OpenCart stock) found the `<select id="input-sort">` dropdown only listed `p.sort_order / pd.name / p.price / p.model` — no "Newest" option. A strict Mistake-2 read would have concluded no date sort exists and routed the site to `full-catalog-sweep`. But OpenCart's stock `product/category` controller accepts ANY `p.*` or `pd.*` column server-side — the dropdown is a UI convenience, not an exhaustive whitelist. Directly hitting `?sort=p.date_added&order=DESC` returned newest-first results (verified by ID-jump: default product_id 22944 → sorted 24005, higher = newer since OpenCart autoincrements). Lesson: on OpenCart, the sort audit is a TWO-step process — (1) read `<select id="input-sort">` and try those values per Mistake 2, (2) even if no date option is visible, ALSO probe `p.date_added`, `p.product_id`, `p.date_modified` with `&order=DESC` and verify via ID-jump. The UI dropdown being silent is NOT evidence the column is unsupported. Ref: playbook Mistake 21.

- **Magento sort option values are merchant-customizable — NEVER assume `created_at` is universal.** On 2026-04-07 the audit on londerosports.com (Magento 2.x) found a stored `sortParam: '?product_list_order=created_at&product_list_dir=desc'` that Magento silently ignored — `created_at` is not a configured option value on this install, so the sort fell back to the default `bestsellers`. Reading the actual `<select id="sorter">` revealed the newest-first option value is literally `new` (not `created_at`). Other Magento sites use `news_from_date` (ellwoodepps M1.x, site 6), `date_added`, `newest`, etc. The lesson: Mistake 2 (never guess sort params) applies with extra force to Magento. Every Magento audit MUST read `<select id="sorter">` / `<select name="order">` HTML and use the actual `value=` attribute. Verify with ID-jump test (default first product vs sorted first product must differ). When re-verifying Magento sites with stored `product_list_order=created_at` or `order=news_from_date`, treat them as UNVERIFIED and re-read the HTML. Ref: playbook Mistake 20.

- **BC Stencil raw page-1 regex counts are ALWAYS inflated and ALWAYS misleading.** On 2026-04-09 the initial audit of theammosource.com (48,012-product site, largest in the fleet) reported per-category product counts using raw `grep -oE 'data-product-id="[0-9]+"' | wc -l` against page-1 HTML. Three errors compounded: (1) **double-render**: BC Stencil renders each product card TWICE per listing page — once as visible grid card, once as hidden quick-view modal shadow-card, both sharing the same `data-product-id`. Raw regex returns 2× the real unique count. Use `sort -u` OR the production `extractCatalogProducts` which dedupes via URL Set. (2) **Page-1 counts are NOT totals**: must walk pagination end-to-end. BC Stencil perPage varies 20-52 per theme; walk `?page=2, 4, 8, 16...` doubling until extraction returns 0, then binary-search. (3) **Sort verification needs a 3-outcome decision tree, NOT 2**: `honored` (newest != default), `honored (default=newest)` (newest == default but alphaasc differs — false negative trap, many BC Stencil stores default to featured which equals newest), `noop-small` (category ≤20 products, normal BC Stencil behavior, not a bug). ALWAYS use `?sort=alphaasc` as counter-control — if you only test `newest vs default` and see identical results, you've produced a false negative. Reference: `backend/src/services/scraper/adapters/generic-retail.ts:512-610` (extractCatalogProducts dedupes via URL Set), playbook Mistake 29.

- **Wix Stores sub-category URLs silently leak pagination to global `/shop` order.** On Wix Thunderbolt sites, sub-category URLs like `/fishing` render a filtered page 1 correctly, but `/fishing?page=2` silently returns `/shop?page=2` (not fishing-filtered). Category filtering is React client-side state only; pagination hrefs in the SSR output point to global `/shop?page=N`. Walking sub-category URLs with pagination produces hybrid junk (page 1 filtered + subsequent pages global) — creates dedupe noise and fake coverage metrics. Fix: for any Wix Stores site, use ONLY the top-level `/shop` URL with `?page=N` (1-indexed, `perPage=20`, `firstPageHasParam: false`). Wix product URLs (`/product-page/<slug>`) are globally unique so no category partitioning is needed. Detection: `<?xml ... generatedBy="WIX">` in `/sitemap.xml` + `server: Pepyaka` header + homepage contains `wixBiSession`/`thunderbolt`. Sort: no URL param exists (React client-side only), use `full-catalog-sweep`. Product count via Wix-specific `/store-products-sitemap.xml`. Ref: playbook Mistake 27.

- **LightSpeed eCom (hosted) silently ignores `?page=N` — pagination ONLY works via `pageN.html` suffix, and when `sortParam` is also present the suffix template must bake the sort into it.** On 2026-04-08 the audit on solelyoutdoors.com (LightSpeed eCom hosted, shop 613284, Nova theme) found that `/firearms/non-restricted/?sort=newest&page=2` returns IDENTICAL products to page 1. The only working pagination form is `page2.html` (suffix-replace, matching the fulcrum-outdoors site 9 + gagnonsports site 11 precedent). Compounding this: `GenericRetailAdapter.getNewArrivalsUrls` at `generic-retail.ts:215-220` appends `profile.sortParam` (`?sort=newest`) to every catalogUrl before handing them to the watermark crawler. When `buildPaginatedUrl` (`catalog-crawler.ts:127-136`) then tries the default fallback `suffix-replace` with `match: '.html'`, the URL `/firearms/non-restricted/?sort=newest` doesn't end with `.html` → falls into the append branch → produces `/firearms/non-restricted/?sort=newestpage2.html` (garbage). The fix is a pagination pattern that explicitly matches the sort query segment: `{type: 'suffix-replace', match: '?sort=newest', template: 'page{N}.html?sort=newest'}`. With this pattern, the WITH-sort case (T1 watermark URLs from `getNewArrivalsUrls`) strips `?sort=newest` and appends `page{N}.html?sort=newest` correctly, AND the BARE case (T2-4 catalog URLs from `getCatalogUrls`) falls to the append branch producing `/firearms/non-restricted/page2.html?sort=newest` which ALSO works because the trailing `/` joins cleanly with `page2.html`. Lesson: when a site has BOTH a sortParam that the adapter appends AND a suffix-replace pagination scheme, the `paginationPattern.match` MUST anchor on the sort query segment, not on `.html`. Always live-test `?page=N` against the same sorted URL and compare first-product slug against page 1 BEFORE trusting any generic query-pagination assumption. Reference: playbook Mistake 26, `catalog-crawler.ts:118-166`, `generic-retail.ts:209-239`.

- **Never trust a previous agent's root-cause diagnosis — verify against the live HTML.** On 2026-04-06 a verification agent diagnosed ellwoodepps.com firearm pages as having a "custom firearm-table layout that confuses extractTitle". A second agent was nearly sent to add specialized selectors. The actual bug was 7 lines away in `extractCatalogProducts` (`generic-retail.ts:444-451`): Magento 1.x product URLs end with `/category/NN/` (a breadcrumb segment), which made `isNavUrl()` reject them as category pages. The existing `.products-list .item` selector and `extractTitle()` were already correct — the products were being matched, then dropped by the URL filter. The fix was a one-line whitelist for `/catalog/product/view/id/\d+/`. Lesson: always run the production adapter against fresh HTML AND log what gets dropped at each step (selector match, title extract, link extract, isNavUrl, isCategoryUrl) before believing any "the selector doesn't work" claim. The bug is often in the filter, not the selector. Reference: ellwoodepps.com profile and `generic-retail.ts:444-451`.

- **Shopify `/products.json` sorts by `published_at`, NOT `created_at` (Mistake 32).** When checking API sort monotonicity, test ALL timestamp fields — `created_at` had 113 violations on fishingworldgc while `published_at` had 0. Shopify's `created-descending` sort label is misleading; watermark crawler must use `published_at` as `postDate`.

- **Platform tags: use vendor-specific names, and match the platform-sort map by substring, not equality (2026-04-14).** The fleet already uses vendor/version-specific tags (`bigcommerce-stencil`, `bigcommerce-blueprint`, `magento-1.x`, `magento-2.x`, `ecwid-on-wordpress`, `lightspeed-classic`, `lightspeed-ecom`, `hikashop-joomla`). Always prefer the informative tag (`celerant-coldfusion` over `coldfusion`) — it signals which crawler quirks are vendor-specific vs runtime-generic, and it's what future auditors will verify against HTML markers per playbook Mistake 22. The `platformSortMap` in `generic-retail.ts:228` previously used STRICT equality with engine-family keys (`bigcommerce`, `magento`, `lightspeed`, `coldfusion`) — meaning ~15 fleet sites with vendor-specific tags were getting `(undefined)` from the map. This was silently masked because `sortParam` from the profile takes precedence. Fixed 2026-04-14 to use substring match (`platform.includes(key)`), so `celerant-coldfusion` → `coldfusion` sort, `bigcommerce-stencil` → `bigcommerce` sort, `magento-2.x` → `magento` sort all resolve correctly. Lesson: when a map key and stored values live in different places, strict equality is a trap — always prefix/substring match, or centralize the tag vocabulary.

- **Theme name ≠ platform name; verify CDN host, not theme name (Mistake 39, 2026-04-26).** During Phase 3 Task 3.5 Set 2 detector smoke against gagnonsports.com, the audit history (and `seed-sites.ts:85`) labeled the site as "LightSpeed Classic" — but live HTML showed `cdn.shoplightspeed.com/shops/626968/themes/9544/` (the modern eCom CDN host) plus the Lightspeed Netherlands B.V. copyright string. Root cause: an older theme name ("InStijl Dream Theme") on a MODERN LightSpeed eCom store had been mistaken for the legacy LightSpeed Classic platform. The legacy Classic platform actually used `cdn.webshopapp.com/shops/<id>/themes/` (SEOshop/webshopapp.com infrastructure), which gagnonsports has NONE of. **Lesson**: when distinguishing between platform variants/generations (Classic vs eCom, Blueprint vs Stencil, M1 vs M2, BC vs Magento), the distinguishing marker MUST be on the CDN host or runtime infrastructure, not the theme name. Theme names propagate forward across platform migrations; CDN hosts and runtime versions do not. **Companion**: same Phase 3 found that `frontierfirearms.ca` had MIGRATED from BC Blueprint to BC Stencil since the prior session's audit — site updated 14 days into the modular probe rebuild work. **Audit memory is point-in-time**, but for platform-detection specifically, ALWAYS verify the CDN host and meta-platform tag against current live HTML before trusting any stored platform tag.

### Audit methodology
- **DB=0 sites need ALL stale profile signals re-verified against live HTML before any other audit work.** On 2026-04-08 surplusherbys.com was found to have been silently broken for weeks with DB=0. Root cause was THREE compounding stale signals in the profile, none ever verified against live HTML: `platform: 'generic-retail'` (wrong, actually `wix-stores`), `hasCaptcha: true` (wrong, verified false via heavy probe), `notes: "uses FastSimon search"` (wrong, no FastSimon anywhere on the site). Individually any one of these might not have broken the site; combined they caused the bootstrap crawler to flag the site as unreachable and skip indexing. **Mandatory rule for any DB=0 site**: the FIRST actions of the audit must be (1) heavy 8-batch WAF probe, (2) grep live HTML for platform markers (grep for ALL known platform signatures, don't trust stored `platform`), (3) re-verify EVERY free-text `notes` claim against live HTML (search for the specific technology/vendor mentioned; if absent, the note is stale and must be deleted), (4) check `/sitemap.xml` + `/robots.txt` for actual sitemap path, (5) walk homepage with production adapter before trusting stored `catalogUrls`. Treat DB=0 sites as fresh onboarding, NOT re-verification. Why: each piece of profile metadata is a decision input for the crawler. Wrong signals compound via anchor bias — each wrong signal "confirms" the others by association. Ref: playbook Mistake 28.

- **Subagent API accessibility claims MUST be independently verified (Mistake 33).** A subagent fabricated an HTTP 405 on internationalshootingsupplies.com's WP REST API (actually returns 200 with 5,111 products), nearly causing an incorrect `woocommerce → generic-retail` adapter downgrade. Always run one verification curl before applying any subagent-recommended adapter/method change.

- **catalogUrls must cover 100% of products. NEVER drop small categories.** 92% coverage was rejected by user on truenortharms.com (2026-04-10). If parents are non-inclusive (e.g. BC Stencil themes that show subcategory tiles instead of child products), include ALL leaf categories — even those with 1 product. The goal is EVERY product reachable by the crawler. "Minimum overlap" means don't duplicate, NOT "skip small ones."

## Rules
- Always read code before modifying — never assume how something works
- Run `npx tsc --noEmit` after changes to verify types
- On Windows: write `.js` script files instead of inline `node -e` with `$disconnect`
- Use `prisma db push`, never `prisma migrate`
- Test adapters against live sites before claiming they work
- After any crawler change, verify with actual crawl data — not "should work"
- Use existing app services (`scrapeWithAdapter`, `searchProductIndex`) — don't reimplement
