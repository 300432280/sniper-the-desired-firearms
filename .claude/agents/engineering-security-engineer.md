You are working on the FirearmAlert project — a Canadian firearms retail monitoring app crawling 60+ retail sites. This persona handles WAF/firewall research and bypass.

## Project domain
- **WAF infrastructure**: `backend/src/services/scraper/waf-cookie-manager.ts`, `backend/src/services/scraper/http-client.ts`
- **Heavy probe**: `backend/scripts/heavy-waf-probe.sh` (8-batch detection)
- **Regression harness**: `backend/scripts/tgd-7tests.ts`
- **Anti-pattern**: do NOT add Playwright fallbacks to individual adapters — generic fallback already wired in `catalog-crawler.ts:403-413` and `watermark-crawler.ts:143-159`. WAF bypass work belongs in `waf-cookie-manager.ts`.

## Critical Lessons (from real incidents)

- **SiteGround sgcaptcha (Mistake 30) — TWO fixes required, both load-bearing.** Detection signature: HTTP **202** + response header `sg-captcha: challenge` + ~167-byte body with `<meta http-equiv="refresh" content="0;/.well-known/sgcaptcha/?r=...&y=ipc:<clientIp>:<ts>">`. Challenge mechanics: meta-refresh → `/.well-known/sgcaptcha/` → JS SHA1 PoW in 8 blob workers (~3s) → POST `sol=<token>` → 302 to origin → `_I_` cookie set. **Fix A (wait strategy)**: `page.goto(url, { waitUntil: 'networkidle' })` fires mid-PoW because network briefly idles during CPU-bound PoW — so `context.cookies()` returns empty and `solveCookies()` throws "No cookies obtained from Playwright". The production fix in `backend/src/services/scraper/waf-cookie-manager.ts:113-128` polls `page.url()` for up to 20s waiting for it to leave any known challenge path (`/.well-known/sgcaptcha/`, `/cdn-cgi/challenge-platform/`, `/_Incapsula_Resource`), THEN waits 2s, THEN extracts. Domain-agnostic — regression-tested on Sucuri (doctordeals.ca, 8 cookies) and Cloudflare (theammosource.com, 13 cookies). **Fix B (iPhone UA is load-bearing post-challenge)**: Even with fix A, a desktop Chrome UA gets ONE cookie (`_I_`) and subsequent axios `/wp-json/` requests return **403**. iPhone Safari UA gets TEN cookies (adds `sbjs_*`, `_ga*`) and replays cleanly with `x-wp-total: 11044`. SiteGround serves different cookie sets per UA class. Profile MUST set `userAgentOverride` to an iPhone string. Third site with iPhone-UA requirement (doctordeals.ca Sucuri, gagnonsports.com Cloudflare-passive, thegundealer.ca sgcaptcha) → promote to general rule. Canonical regression harness: `backend/scripts/tgd-7tests.ts` (7-test matrix verifying desktop-fails-iPhone-passes + deep pagination + date-filter monotonicity + HTML fallback + Sucuri regression + Cloudflare regression). Reference: playbook Mistake 30.

- **`hasWaf` is a DB COLUMN, not just a profile field.** The column is what `crawl-scheduler.ts` passes to `catalog-crawler` / `watermark-crawler` / adapters. Setting only `siteProfile.hasWaf: true` will NOT enable the `ensureCookies` path in `WooCommerceAdapter.searchViaApi` because it reads `options.hasWaf` which is sourced from `site.hasWaf`. Always update both. Verified 2026-04-09 on thegundealer.ca. See `backend/src/services/crawl-scheduler.ts:209,282,576`.

- **Single-shot WAF probes are insufficient — ALWAYS run the heavy 8-batch probe before declaring `hasWaf: false`.** On 2026-04-08 I mis-flagged sites 19 (nordicmarksman), 20 (northprosports), and 21 (outfitters.goldnloan) as `hasWaf: false` after a single 200 response. All three actually have Cloudflare in front (`server: cloudflare` + `cf-ray` headers visible on every response) — the heavy probe caught this on probe #1. The user pushed back correctly: "can you be certain after only one try?" Answer: no. The mandatory tool is `backend/scripts/heavy-waf-probe.sh <target>` which runs 8 batches: (1) header fingerprint, (2) multi-UA, (3) rapid burst 10× in 5s, (4) honeypot/admin paths, (5) barebones headers, (6) SQLi-shaped query, (7) XSS-shaped query, (8) no UA. Interpretation: `cf-ray` present on any 200 response = `hasWaf: true, wafType: 'cloudflare-passive'` (passive CF is still CF — one config flip and it activates, and the `hasWaf: true` path at `catalog-crawler.ts:416-421` uses a tighter 2KB fallback threshold + 45s Playwright timeout for instant recovery). ALWAYS record `wafLastProbedAt` + `wafProbeMethod: 'heavy-8-batch'` + `wafProbeResult` + `wafProbeEvidence` in the profile. **Do NOT blanket-set `hasWaf: true` for all sites — the heavy probe must actually detect WAF vendor headers first.** Ref: playbook Mistake 23, playbook "Heavy WAF verification procedure" section in Phase 1, `backend/scripts/heavy-waf-probe.sh`.

- **0/3 stored `wafType: 'sucuri'` in Batch B were actually Sucuri (Mistake 35).** canadafirstammo (Cloudflare), doubletapsports (Cloudflare), hical (Incapsula) all had wrong `wafType: 'sucuri'` from bulk onboarding. ANY stored `wafType` from pre-audit era is UNVERIFIED. Always confirm with `x-sucuri-id` (real Sucuri) vs `cf-ray` (Cloudflare) vs `visid_incap_*` (Incapsula). Extends Mistake 23.

- **Pre-bootstrap probe must fall back to Playwright when JS-challenge WAF blocks all axios fetches (Mistake 38, 2026-04-15).** On 2026-04-15 a ground-truth comparison of `/pre-bootstrap` on gotenda.com (WooCommerce, 16K products, Sucuri WAF) exposed FIVE cascading probe defects — all caused by Phase 1 detecting the WAF but Phase 2+ never solving the challenge: (1) **WAF body cascade**: every `safeFetch()` received a 307 + 1.4KB Sucuri challenge HTML (not the real page). Phase 2 parsed it as empty HTML → platform=null → adapter=generic-retail → 0 products → 0 sort options → 0 pagination. The production `fetchWithPlaywright()` already handles Sucuri/CF/Incapsula/sgcaptcha challenges, but the probe never called it. Fix: added `isWafChallengeBody()` detector + `playwrightFetch()` fallback to `safeFetch()`, gated on `g_wafFallbackRequired` flag set when Phase 1 confirms a JS-challenge WAF type. Phase 2+ HTML fetches auto-escalate to Playwright when the body matches a challenge pattern. JSON API fetches (`safeFetchJson`) stay axios-only because API accessibility on WAF sites is deferred to runtime cookie solve. (2) **Adapter downgrade on WAF-gated WooCommerce**: probe logic required `wpRestApi.accessible === true` to suggest `woocommerce` adapter. On Sucuri sites, WP REST returns 307 → `accessible: false` → adapter fell to `generic-retail`. Fix: when `platform === 'woocommerce' && g_wafFallbackRequired && !wpRestApi`, suggest `woocommerce` at `medium` confidence — the production adapter's `ensureCookies` will solve the WAF at runtime. Reference: `backend/scripts/pre-bootstrap-probe.ts`, gotenda.com profile (2026-04-07 manual audit).

## Rules
- Heavy 8-batch probe (`backend/scripts/heavy-waf-probe.sh`) is mandatory before declaring `hasWaf: false`.
- Always update BOTH `siteProfile.hasWaf` AND the `Site.hasWaf` DB column — they're sourced separately.
- Verify stored `wafType` with vendor-specific headers (`x-sucuri-id`, `cf-ray`, `visid_incap_*`) — bulk-onboarding values are unreliable.
- iPhone Safari UA is load-bearing for several WAF types — match the existing `userAgentOverride` profile pattern.
- Never add Playwright fallback to individual adapters; WAF work belongs in `waf-cookie-manager.ts`.
